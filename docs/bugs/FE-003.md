# FE-003

## Title

Frontend `s1_pcReg` does not boot from `resetAddr` when `resetAddr` is not `0`.

## Status

fixed

## Symptom

When `BreezeCore.io.resetAddr` is poked to a non-zero value (e.g. `0x800`), the frontend still starts fetching from address `0` instead of the expected `0x800`.

Observed failure pattern:

- `dut.io.resetAddr.poke(0x800L.U)` — top-level IO reports `2048`
- After reset deassert, `frontendDebug.s1_pcReg` reads `0`
- Subsequent fetch PCs are `0, 4, 8, 12, ...` instead of `0x800, 0x804, 0x808, ...`

## Expected

When `resetAddr` is driven to `0x800` during reset, `s1_pcReg` should be initialized to `0x800`. The frontend should begin fetching from that address.

## Repro

Dedicated reproduction testcase:

- `design/src/test/scala/core/breezecoreSpec.scala`
- `flow.core.BreezeCoreNoFASESpec`
- `"BreezeCore should boot from resetAddr 0x800"`

Run:

```bash
cd design
sbt "testOnly flow.core.BreezeCoreNoFASESpec -- -z 'boot from resetAddr'"
```

Test behavior:

1. `resetAddr` is poked to `0x800` before and during reset.
2. `nextLevelReq` is monitored; responses are returned from a small memory map (`0x800` and `0x0` both mapped to the same program so ESTOP fires regardless).
3. After ESTOP, the test asserts that the first retired PC was `0x800`.

## Evidence

Debug output from the reproduction test:

```
[DEBUG] resetAddr_raw=2048
[DEBUG] after deassert: s1_pcReg=0
```

Assertion failure:

```
Some(0) was not equal to Some(2048)
```

## Current Hypothesis

The RTL connection looks correct on paper:

- `BreezeCore.io.resetAddr` is connected to `BreezeFrontend.io.resetAddr` via `frontend.io.resetAddr := io.resetAddr`
- `BreezeFrontend` sets `s1_pcReg := io.resetAddr` during `reset.asBool`

However, the ChiselSim poke on the top-level `io.resetAddr` does not appear to propagate to the sub-module port, or the `when(reset.asBool)` assignment is not overriding `RegInit(0)` as expected.

Possible causes:

1. `RegInit(0.U)` takes precedence over the `when(reset)` conditional write in this Chisel/CIRCT version
2. ChiselSim's `poke` on a parent-module port does not propagate through `:=` connections into sub-module ports
3. The reset signal reaching the frontend is not aligned with the `poke` timing

## Resolution

The root cause was hypothesis #1: `RegInit(0.U)` and `when(reset) { s1_pcReg := io.resetAddr }` are conflicting reset paths. In ChiselSim (Treadle), `RegInit` takes precedence over the `when(reset)` body, so `s1_pcReg` always resets to `0` regardless of `io.resetAddr`.

Fix: changed `s1_pcReg`, `s2_pcReg`, `s3_pcReg` from `RegInit(0.U)` to plain `Reg()`. The `when(reset)` block already initializes these registers, making `RegInit` redundant and harmful.

```scala
// Before:
val s1_pcReg = RegInit(0.U(cfg.VLEN.W))  // always resets to 0
// After:
val s1_pcReg = Reg(UInt(cfg.VLEN.W))     // reset value comes from when(reset) block
```

Verification:
```bash
cd design && sbt "testOnly flow.core.BreezeCoreNoFASESpec"
# Tests: succeeded 3, failed 1 (trap test still expected to fail)
# "boot from resetAddr 0x800" now PASSES
```
