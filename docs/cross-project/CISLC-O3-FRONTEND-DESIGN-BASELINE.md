## 1. 一页总览

```text
         ┌─ uBTB：快速给出下一预测地址，连续每拍推进 ─┐
预测 PC ─┤                                              ├─ FTQ
         └─ 主 BTB：两拍 ─┐                            │  元数据/身份/检查点
             TAGE：三拍 ─┴─ 慢预测检查、覆盖及重定向 ───┘
                                                           │ demand 游标
                                                           v
                   ICache S0 → S1 → S2 → S3
                                      │ 数据/异常/身份
                                      v
                        原始取指返回队列（暂定 8 项）
                        data_ready && slow_done && !killed
                                      │ 按程序路径顺序出队
                                      v
                   F0：跨块拼接、识别长度、RVC 展开
                                      v
                   F1：预解码、直接目标核对、预测修正
                                      v
                   指令 buffer → 每拍最多交付 4 条

FTQ 独立 prefetch 游标 → 地址转换复用/提前翻译 → L1 查询/过滤
                     → L2 请求 → ICache 回填
```

FTQ 保存预测与生命周期元数据，指令字节放返回队列及后续指令 buffer。FTQ 不充当取指数据存储器。

## 3. 预测块、槽位、指令数

### 3.1 16B 的含义

- `region_base = PC & ~0xf`；半字槽位 `slot = PC[3:1]`，范围 0…7。
- 16B 最多包含 8 条 16 位指令，或者 4 条完整 32 位指令；混合长度时不同。
- 跳转落点可以在区域中间，FTQ entry 仍对应这个对齐区域，但有效起点不一定为槽位 0。
- 预测选中块内跳转时，其后的槽位不属于这次动态取指路径。
- 同一个区域可能多次动态进入，每次是不同的 FTQ 身份。
- 一条 32 位指令的后半字不能被当作独立指令或分支槽位。

因此 16B 是字节带宽，不是稳定四条指令的保证。顺序、对齐且全为 32 位指令时才有每块四条；中途分支、落点偏移、跨块指令都会降低有效产出。8 条 RVC 是这一块的容量上限，不代表后端一拍接收 8 条。

### 3.2 mask

逻辑上区分：入口之前的无效槽位、指令起始槽位、条件分支槽位、JAL 槽位、选中跳转之后的无效槽位。可以组合编码，但不能混淆语义。BTB 中的类型信息是预测信息，最终需要预解码验证。

### 3.3 跨 line / 跨页

对齐的 16B 普通 cache 请求本身不会跨 64B line，也不会跨 4KiB 页。但 `region_base+14` 开始的 32 位指令会跨 16B，位于 line/page 末尾时也会跨 line/page。

F0 保存前半字并等待顺序地址的后半字，原指令 PC、长度、归属 FTQ 身份必须保持。预测该指令会跳转，也不能用预测目标处的数据代替顺序后半字。

**待定**：跨块补半字的辅助请求如何占用返回队列和 FTQ 资源；后半字异常如何携带原指令 PC 与故障地址；与普通顺序请求合并的规则。

## 4. uBTB、主 BTB 与 TAGE

### 4.1 快慢预测时序

以“C0 发起、C2 末得到三阶段结果”作相对示意，最终接口应统一寄存器边界口径：

| 周期 | 快速预测 | 主 BTB | TAGE / 动作 |
| --- | --- | --- | --- |
| C0 | A 给出下一块 B；为 A 分配 FTQ entry | A 开始 | A 开始 |
| C1 | B 给出 C；为 B 分配 entry | A 结果 | A 中间阶段 |
| C2 | C 给出下一块 | 保存/对齐 A 目标信息 | A 慢结果，检查是否覆盖 |

这里是不同预测块每拍经过快速预测器，并有多笔慢预测在途；不是要求 uBTB 自身必须做成三拍。

主 BTB 的目标、CFI 位置和类型与 TAGE 方向结果对齐，在慢预测出口联合选择下一 PC。TAGE 给出条件分支方向，**不直接生成跳转目标，也不是真实执行结果**。

uBTB 结果使预测能够先行。即使前面的 ICache 请求 miss，后面的 FTQ entry 仍可完成慢预测；慢预测有机会在这些 entry 真正取指前消除错误路径。这是解耦的预期收益。

**待定**：uBTB 容量、映射方式、字段和训练细则。直接映射、链接后继或提前读下一 entry 曾讨论，未全部定案。

### 4.2 主 BTB

已选“一个区域 entry 一个目标”，不是每槽位各存目标，也不是每 entry 两个目标。概念字段：

| 字段 | 用途 |
| --- | --- |
| valid / region tag | 区域匹配 |
| br_mask[7:0] | 预测的条件分支位置 |
| jal_mask[7:0] | 预测的直接无条件跳转位置 |
| cfi_idx[2:0] | 所存目标属于哪个槽位 |
| cfi_type | branch / JAL / JALR / call / return 等所需分类 |
| target | 唯一存储的目标 |
| RAS action / length 等 | 支持推测 RAS；实际编码待定 |

mask 知道多个分支位置，不代表拥有它们的全部目标。所选 taken 分支只有在目标归属槽位匹配时，才能使用该 target。

目标更新采用最近一次**提交的 taken CFI**。没有 taken 时保留旧目标。应分别统计：同区域不同 CFI 争用唯一目标、同一个 JALR 目标变化、不同区域之间的容量/映射替换。

主 BTB 容量、路数、替换策略待定。大 SRAM 表可以组相联；“单目标”不等于“直接映射”，4-way 与一个 entry 一个目标是两个独立维度。

### 4.3 目标缺失

条件分支 TAGE 输出 taken 但没有匹配目标时，初版继续顺序路径。保留 `raw_pred_taken` 与 `target_missing`，不能在统计里把它说成 TAGE 预测 NT。

后续预解码可计算 branch/JAL 的直接目标并修正。普通 JALR 若无可用目标，等待执行得出真实目标。表的持久训练仍遵循提交策略。

taken-only 推测历史应反映实际采用的预测路径：因目标缺失而沿顺序取指时不能假装已经走了那个 taken edge；纠正时恢复并重新推进历史。

### 4.4 TAGE 组织

一次用预测区域 PC 及该块入口历史，产生 8 槽位的条件方向结果。只有有效的条件分支起始槽位使用这些位，再按程序顺序选择有效控制流出口。

“八位向量”是输出形式，不等于只需一份单比特状态；表内可以是每行含 8 槽位状态，实际 SRAM 宽度、tag 和有效位组织待定。若说 1024 行且每行 8 槽位，就不能按只有 1024 个预测状态估算资源。

历史长度指数增长不要求各表行数相同；允许长历史表行数更少。D22 暂定六张 tagged 表使用 4/8/16/32/64/128 次事件窗口，历史单位见第 5.4 节；这不冻结容量。之前讨论过各表 1024、base 2048 等数值，仍未选定。

SC、loop predictor、ITTAGE 不是第一版已选功能。

## 5. 历史：事件范围已定，第一版函数暂定

### 5.1 三个独立问题

1. **事件选择**：第一版仅 taken 条件分支使历史推进；NT、JAL、JALR、call/return 均不推进历史。
2. **历史表示与更新**：保存事件序列，还是仅保存持续移位/XOR 的压缩状态？
3. **查表折叠**：把某张表使用的历史压到 index/tag 所需位数，再与 PC 混合。

不要把“更新历史时 hash 地址”和“查询时折叠历史”当成同一个步骤。

### 5.2 讨论过的路径 hash

参考 Arm FDIP 论文讨论过：

```text
event_hash = (branch_PC >> 2) XOR (target_PC >> 3)
H_next     = ((H << 2) XOR event_hash) AND history_width_mask
```

这仅记录参考公式，不是已批准 RTL。RVC 下 PC bit1 有信息，不能未经分析直接丢掉。此前待定的事件编码、地址选位及多表使用方式，现由第 5.4 节 D22 给出第一版暂定函数；该函数不是原式的等价改写。`branch_PC` 是实际选中指令的 PC，不是简单使用 16B 区域起点。

曾提出两种方案：

- 保存一个滚动 hash 寄存器，各表取不同宽度的信息再折叠：状态与恢复较简单，但“低 N 位”不等于“最近 N 次事件”。
- 保存最近若干次 taken 事件的固定宽度 hash，各表使用最近 N 次事件并维护折叠值：历史窗口意义明确，需要事件存储、出窗处理与恢复设计。

前一方案曾被建议为初版，但未获最终确认。2026-09-30 的 D22 暂定采用后一方案，具体函数见第 5.4 节。上面的持续移位/XOR 公式保留作为论文参考，不作为 D22 的历史存储更新式；两者不等价。

### 5.3 JAL 与历史

JAL 无条件跳转，无需 TAGE 学它是否 taken；BTB 提供提前使用的目标，预解码能计算直接目标。条件 branch 则需要 TAGE 的方向和 BTB 的提前目标共同工作。

**2026-09-30 决定（D09）：第一版不把 JAL、JALR、call/return 纳入历史，只纳入 taken 条件分支。** 先前“所有 taken 控制流都加入”的建议未被采用。无条件跳转仍由 BTB/RAS 等提供目标，其正常目标预测、训练及 RAS 操作不因排除历史而取消。

沿推测路径，只有被实际选为 taken 且具有可用目标的条件分支触发该路径 hash；真实结果不同时按恢复流程纠正。NT 不插 0。预测、慢覆盖、预解码/执行恢复及提交参考历史必须使用同一事件资格规则，不能在恢复时偷偷加入 JAL/JALR。

保留后续实验决策点：比较“只纳入 taken 条件分支”与“也纳入无条件跳转”的实际效果。当前不实现第二种模式，也不声称第一种准确率更高。比较时保持其他参数和工作负载一致，观察条件分支方向误预测率、前端不足四条的周期、整体 IPC，以及资源/时序代价；沿用第 12 节事件口径，必要时补充按指令类型的历史更新事件。根据测量结果再修改 D09。

不要称 BOOM、香山已经采用本设计这套 taken-only PC/target 公式。参考实现的方向历史与本设计拟采用的路径历史需要分别说明。

### 5.4 D22：第一版可实现的事件编码与折叠函数（暂定）

**2026-09-30 决策依据**：用户要求给出具体可用的第一版，并把函数作为可根据实际预测率改进的决策点。以下为本设计的暂定构造，没有准确率、综合或 FPGA 证据，不宣称它优于论文公式。

#### 事件编码与存储

定义 `fold_w(X)`：将有限宽度无符号数 X 从低位开始切成 w 位段，最高不足 w 位的段补零，各段 XOR。`rol_w(X,k)`：在 w 位内循环左移 `k mod w` 位，结果限制为 w 位。所有地址按工程实际 PC 位宽解释，不做带符号移位。

```text
B = fold_8(branch_PC >> 1)
T = fold_8(target_PC >> 1)
e = B XOR rol_8(T, 1)
```

只去掉恒零的 bit0，保留 RVC 的地址 bit1；branch_PC 是实际选中条件分支的指令地址，target_PC 是实际采用的目标。两个地址的贡献可能碰撞，这是压缩编码的代价，不是完整地址保存。

逻辑上保存最近 128 个 8 位事件编码，`E[0]` 最新，`E[127]` 最老；复位为零。符合 D09 的新事件到来时：

```text
E_next[0] = e
E_next[a] = E[a-1]       // a = 1..127
```

NT、JAL、JALR、call/return 不推进 E。硬件可采用环形存储实现该逻辑，指针每次推进一次。六张 tagged 表暂定 `L_i = 4,8,16,32,64,128`，单位是最近 L_i 次符合 D09 的事件，不是指令数、周期数或历史 bit 数。尚未出现的事件按零处理。

#### 每张表的历史折叠

对历史长度 L、折叠宽度 w，定义：

```text
C(L,w) = XOR over a=0..L-1:
           rol_w(fold_w(E[a]), 2*a)
```

事件越老，编码的循环移位位置不同；移位量 2 是本版暂定的混合参数。该函数只使用所定义的 L 次事件；循环移位和 XOR 会碰撞，不能从 C 还原事件序列。

正常更新不必重新读取整个窗口。令 `e_out = E[L-1]`，即更新前该表最老的事件，则严格等价的增量式为：

```text
C_next(L,w) = rol_w(C(L,w), 2)
              XOR fold_w(e)
              XOR rol_w(fold_w(e_out), 2*L)
```

最后一项消除出窗事件在整体循环移位后的贡献。新旧 C 的边界必须与 E 的边界一致；环形存储应在写入覆盖之前提供 e_out。即使多个表都更新，也只向事件序列追加一次。

#### index/tag 函数

表 i 有 `2^n_i` 行、tag 宽度 `t_i >= 2` 时，维护三个折叠值：`C(L_i,n_i)`、`C(L_i,t_i)`、`C(L_i,t_i-1)`。容量和 tag 位宽仍是独立待定参数，不因本节默认成 1024 行或某一固定 tag 宽度。

```text
P = region_base >> 4

index_i = fold_n_i(P) XOR C(L_i,n_i)

tag_i = (fold_t_i(P)
         XOR C(L_i,t_i)
         XOR (zero_extend(C(L_i,t_i-1)) << 1))
        AND ((1 << t_i) - 1)
```

P 使用 16B 区域地址；槽位仍由 PC[3:1] 和行内槽位状态区分。不同宽度的 tag 折叠用于使 index 碰撞与 tag 碰撞不完全同步，不保证消除别名。有效位、tag/槽位共享方式仍按第 4.4 节另行确定。

所有表使用区域入口的 E/C 上下文产生 8 槽位方向。被选中的 taken 条件分支用于更新后续区域的历史，不提前注入本区域的查询上下文。无目标而采用顺序路径时不更新。

#### 时序、资源、恢复与评估边界

- 事件序列内容为 `128*8 = 1024 bit`，不含指针、端口、检查点、训练元数据和提交参考副本。单个上下文的折叠寄存器总计 `sum_i(n_i + 2*t_i - 1)` bit。
- 更新逻辑是固定循环移位和 XOR；查表读取已经维护好的折叠值，按 D02 的三拍安排 index 生成、阵列访问与 tag/provider 选择。每次更新仍需取得六个窗口边界事件，不能把存储容量小等同于端口代价小；reg 阵列、多读 mux 或复制方案待综合比较。
- 推测恢复必须恢复 E 的实际内容和 C；只恢复环形指针不足以修复已被覆盖的数据。D23 已选完整入口快照，见第 6.4 节；FTQ 保存快照或关联到独立快照存储，慢预测与提交训练使用原查询上下文。存储组织、端口和恢复带宽仍待定，不能默认为零成本。
- D22 保留完整事件窗口以明确各表的历史长度，资源高于只保存一个滚动 hash。若以后改用滚动 hash，应重写历史长度语义并独立比较，不能视为仅换一个等价函数。
- 后续保持 D09、表容量、训练策略和工作负载一致，逐项比较事件编码、移位混合、窗口长度。主要记录提交路径有效条件分支的方向误预测率，同时观察 provider 分布、target_missing、前端供给、IPC、存储/逻辑资源及关键路径。训练统计需区分 raw_pred_taken 与实际采用路径；只有取得证据后才修订本暂定决策。

算例：`0x100 -> 0x120` 得 e=`0xa1`，`0x204 -> 0x240` 得 e=`0x41`，`0x244 -> 0x180` 得 e=`0xa2`。第三次之后，E 的最近三项是 `[0xa2,0x41,0xa1]`；零初始化的 `C(4,8)=0xa2 XOR rol_8(0x41,2) XOR rol_8(0xa1,4)=0xbd`。这是 D22 的例子，不沿用第 5.2 节参考递推式的数值。

本轮仅做数学一致性检查：固定随机种子 22，400 次事件更新，六种窗口长度、w=2..16，共 36,000 次比较，增量 C 与按窗口重新计算的定义一致，并核对上述算例。该检查不构成 RTL、准确率或时序验证。

## 6. 训练、RAS、恢复

### 6.1 表训练

初版 TAGE/uBTB/主 BTB 在提交时训练。执行一旦发现误预测，应立即重定向并恢复推测历史/RAS，不等待提交。必须保存原预测的训练上下文，不能用提交时的当前全局历史重新查询代替。

预留统一训练接口，后续可以比较执行时训练，但第一版不引入被 squash 的训练回滚。表训练与推测历史更新是两个不同过程。

**待定**：块内多条分支的训练排程、一次提交多条时的带宽、FTQ 释放前训练信息的转存。

### 6.2 D29：RAS 与间接跳转，BOOM 式快速修复（2026-10-02 更新）

- RAS 暂定 16 项，参数化，保存返回 PC；根据指令长度计算 PC+2 / PC+4。
- 按 RISC-V x1/x5 的 rd/rs1 提示区分 push、pop、pop-then-push，不能只把所有 JALR 当 return。
- return 优先 RAS，空栈回退 BTB；普通 JALR 先用 BTB 最后目标。
- 只对实际选中且成功分配的推测路径操作一次，不能因 valid 停留多拍、慢预测再返回而重复操作。
- 允许循环覆盖最旧项。每个 FTQ 区域在推测操作之前保存 `ras_before={top_idx,count,top_addr}`；16 项时索引 4 位、占用数 5 位，空栈时 top_addr 不参与修复。
- 慢预测检查直接使用对应区域保存的栈顶及有效性，不使用已经前进到其他块的当前栈顶。

**本次替换的决定**：用户在核对 BOOM 和论文后确认采用 BOOM 式快速修复。取消原先的 undo log、撤销游标、log 满回压及逐条撤销 FSM；不采用此前候选的持久化推测队列。E/C 完整历史快照仍按 D23 保留。

#### 正常操作与恢复

正常预测按 call、return、pop-then-push 分别压栈、弹栈或先取旧栈顶再弹压；满栈循环覆盖，空栈 return 回退 BTB。每个成功分配的区域只应用一次实际采用路径的操作。

D24 选定重定向赢家后，取消年轻路径，读取对应区域入口 E/C 和 ras_before。恢复 E/C，并仅对真实 taken 条件分支按 D09 注入事件；恢复 RAS 的索引和占用数，将保存的非空栈顶写回原位置，再按修正后的指令类型、原始长度执行一次正确的 RAS 操作：条件分支无 RAS 动作；误识别的 call 撤回后不再 push；真实 call 压入返回 PC；真实 return 弹栈；pop-then-push 执行相应组合。预测类型纠错必须使用核实后的动作，不能沿用错误的 BTB 类型。

#### 恢复时序与资源合同

普通分支恢复的实现目标是：R0 接受唯一赢家并发起检查点读取；R1 获得快照、恢复并修正 E/C 和 RAS；R2 从正确 PC 发起正常预测。此口径从前端接受重定向开始，不包含分支发射、执行、反馈传输和后续 ICache 返回延迟，也不是已验证的频率或整核误预测惩罚。恢复工作量不随错误路径上的 push/pop 数增长。

- E/C 恢复采用宽读取通路，分片并行读出，不逐事件装载；恢复访问优先于竞争的提交训练，训练信息保留等待。
- 首版 RAS 按小型寄存器数组组织，恢复拍支持“旧栈顶修复”和“正确 call 压栈”两个确定写入。同位置时以最终修正结果为准；恢复拍禁止普通推测写入，并提供恢复后栈顶所需的读写旁路。不能以单写口为由静默改回逐步撤销。
- 更老重定向或同位置更高优先级修正可替换当前恢复；检查点返回、状态写入和完成通知须属于当前恢复身份，旧恢复不得覆盖新状态。
- 每个 FTQ 的 RAS 恢复载荷约为 `4+5+V` bit（16 项、返回地址 V 位），不含 FTQ 本身身份及接口开销。RAS 本体、双写选择和旁路资源需综合核对，不能仅以存储 bit 数估算 FPGA 成本。

#### 明确接受的预测精度取舍

只修复保存的栈顶，不保证还原所有深层地址。例：原栈底到栈顶为 `[A,B,C]`，错误路径先 pop 两次、再 push X/Y，恢复后可能为 `[A,X,C]`。第一次 return 可取得 C，之后仍可能因 B 被覆盖而误预测；真实 JALR 执行继续纠错。此为有意接受的预测质量损失，不允许预测目标替代真实执行结果。原“RAS 内容完整恢复”不变量相应收缩为本节合同；历史 E/C 仍完整恢复。

保留 return 命中/错误、空/满栈、修复次数、恢复周期及恢复被替换次数的观测；移除 undo-log 满事件要求。深层污染的具体归因可用仿真参考栈，不宣称硬件能直接识别每次污染。

本轮核对 BOOM v4 固定提交 `54f11b85c9a670ef3dd18bc675994b9a661b06ee`：[FTQ 保存/修复 ras_idx 与 ras_top](https://github.com/riscv-boom/riscv-boom/blob/54f11b85c9a670ef3dd18bc675994b9a661b06ee/src/main/scala/v4/ifu/fetch-target-queue.scala#L298)、[前端 RAS 写回与重定向接入](https://github.com/riscv-boom/riscv-boom/blob/54f11b85c9a670ef3dd18bc675994b9a661b06ee/src/main/scala/v4/ifu/frontend.scala#L945)。该版本不同于此前前端研究的 58ef2720；占用数、双写组织和 R0～R2 是本项目适配决定，不是 BOOM 的原样接口或时序。

### 6.3 慢预测覆盖

对 A 的慢结果：保留 A 的原始 16B 数据，修正 A 的预测元数据与有效范围；如果路径改变，杀掉 A 之后错误路径的 FTQ/请求/返回项，恢复到 A 的检查点并应用修正结果，再从正确下一 PC 预测。

ICache 已接受的错误路径访问可以继续完成，不要求撤销 SRAM 读或取消已发 miss；返回必须被识别为 killed，不能进入有效指令流。

原始数据出队条件至少为 `data_ready && slow_done && !killed`。因此慢覆盖发生时，该块尚未进入 F0/F1；预解码和执行发现的更晚错误仍需要另外的下游 flush。

### 6.4 D23：完整历史快照（已定）

**2026-09-30 决定**：第一版采用方案①，为每个成功分配的 FTQ 区域保存其入口事件序列 E 与所有表折叠值 C 的完整快照。用户确认“选1吧，然后记录，如果资源不够用再尝试2，3”。该决策确定逻辑内容，尚未实现 RTL。

- 快照必须对应本区域更新之前的历史，且早于后续区域推进。FTQ 可以直接存快照，也可以保存指向独立快照存储的引用；快照与动态 FTQ 身份绑定，其生命周期不能早于所需的慢预测、恢复及训练上下文读取。
- E 按 D22 包含最近 128 个 8 位事件；C 包含每张表的三个折叠值。若 E 采用物理环形布局，快照还应保存该布局所需的指针；也可保存按年龄排列的逻辑 E，恢复到规范布局。必须保证恢复后的 E 与 C 一致。
- 路径修正时停止新预测，清除错误路径，装载出错区域的入口快照，再按正确控制流推进历史。正确结果为 NT 时不注入事件；正确结果为 taken 条件分支时，用正确 PC/target 注入一次。JAL/JALR/call/return 仍遵守 D09，不注入这份历史。
- 慢预测查表使用对应区域保存的 C，不能使用已经前进的当前历史。完整快照只恢复历史上下文，错误路径 FTQ、指令及在途预测的清除仍需按原恢复规则处理；已接受 ICache 请求可完成并丢弃返回。
- 不保证整条流水线单拍恢复。2026-10-02 D29 给出从接受重定向起 R0 读快照、R1 恢复修正、R2 正常预测的实现目标，要求宽读取通路；实际时序待验证。可用 `history_restore_done` 或等价握手确认状态可用。RAS 按第 6.2 节改用索引/占用数/栈顶修复，不再逐条 undo，也不改成完整栈快照。

资源公式：每个快照的 E/C 内容为 `1024 + sum_i(n_i + 2*t_i - 1)` bit，另外计算环形指针（如需）、身份、有效位及存储端口等成本。仅作算例：六张表均 n=t=10 时为 1198 bit，约 150B；32 个 FTQ 项共 38,336 bit，约 4.68KiB。该算例不确定 FTQ 深度、表容量或 tag 位宽，没有综合/时序证据。

仅在完整快照资源不足时再评估以下备选，不作为第一版并行实现模式，也未确定二者优先顺序：

| 备选 | 检查点内容与恢复 | 优势 | 代价 |
| --- | --- | --- | --- |
| ② 只保存 E | 保存事件序列，恢复 E 后重新计算各表 C | 每项少存 C | 上述算例仅省 174 bit/项；并行重算增加逻辑/布线，逐事件重算增加恢复延迟 |
| ③ 撤销记录 + C 快照 | 每次覆盖前记录旧事件；检查点保存记录位置和 C，恢复时倒序撤销 E 的修改并装载 C | 每项无需保存完整 E | 共享记录也占存储；需满时回压、提交回收及覆盖安全规则，恢复延迟随撤销事件数变化 |

后续根据完整快照的实际存储、端口和时序结果判断资源是否不足，再决定是否修订 D23；不能仅因出现备选方案而重新打开已定选择。

### 6.5 D24：统一重定向仲裁与恢复（已定）

**2026-09-30 决定**：用户确认采用统一重定向仲裁器。执行分支、预解码修正、慢预测覆盖和提交端系统重定向统一提交请求，再由唯一赢家驱动 PC、清除和恢复；尚未实现 RTL。

请求逻辑内容包括 valid、来源/原因、动态 FTQ 身份及块内位置、target_PC、历史/RAS 检查点引用、清除范围（包含本指令或只清除其后）以及修正后的历史/RAS 操作。具体字段编码待实现。

仲裁规则：

1. 先剔除已被取消或动态身份失效的请求。
2. 提交端已经正式接受的异常、返回等系统重定向优先，它们确定新的架构执行边界；尚未到提交边界的年轻异常不能借用此优先级。
3. 其余请求按程序顺序选最老的；年龄由动态身份和块内位置决定，不按 PC 数值比较，必须正确处理环形指针回绕。
4. 同一位置的修正采用执行结果 > 预解码修正 > 慢预测覆盖。

先产生唯一赢家，再选择整份请求。target_PC、FTQ 清除边界、历史快照及 RAS 恢复信息必须来自同一赢家，不能分别采用不一致的 mux 优先级。可以使用比较器和优先级 mux；若使用 Mux1H，输入选择信号必须已经经过仲裁成为独热，不能直接使用可能同时有效的来源 valid。

接受重定向的同拍，禁止被清除的年轻路径继续分配、交付或修改推测状态，并使相应 FTQ、返回项和指令 buffer 内容失效。后端按同一取消边界禁止年轻指令的相关副作用。已被 ICache 接受的错误路径请求仍按 D17 完成并丢弃返回。

恢复期间锁存获胜请求，停止新预测，恢复 E/C 和 RAS，再应用修正结果并从 target_PC 继续。若恢复期间收到仍有效且更老的请求，替换当前请求并重新恢复到更老的检查点；同位置由更高优先级的来源覆盖。已被取消的年轻请求丢弃。被替换的旧恢复操作不得在随后完成时覆盖新恢复状态，具体恢复控制握手待实现。

**Flow 参考教训（本轮核对源码）**：提交 `d951f6ae4664b665c4077b16950e2b8e609723c4` 将 BreezeBackend 中重叠请求的 Mux1H 改为优先级 MuxCase，并加入较老 WB 重定向对年轻同拍操作的抑制。相关用例为 `design/src/test/scala/backend/BreezeRedirectPrioritySpec.scala`。CISLC-O3 采用程序年龄仲裁，不能直接复制 Flow 顺序流水线的固定阶段顺序。本轮没有重跑 Flow 测试，也不把该修复作为 CISLC-O3 已验证的证据。

## 7. FTQ 内容、游标与请求合同

### 7.1 FTQ entry 是动态取指描述

以下是逻辑信息，不要求全塞进一个 SRAM word；可拆 PC RAM、预测 metadata RAM、状态寄存器等：

| 类别 | 所需信息 |
| --- | --- |
| 身份 | ftq_idx + generation/等价唯一身份，程序顺序关系 |
| 地址范围 | 16B region_base、实际入口 PC/槽位 |
| 预测 | 快预测下一 PC，慢预测结果，选中 CFI 槽位/类型/目标，mask |
| 状态 | valid、slow_done、fetch issued、killed，以及完成/释放所需状态 |
| 恢复 | D23 的块前 E/C 完整历史快照或其引用、D29 的 RAS 入口索引/占用数/栈顶 |
| 训练 | provider、预测计数状态等后续训练所需上下文或其引用 |
| 关联 | 返回队列/请求身份、后端提交关联 |

FTQ 不存 cache 返回的指令数据。返回队列也不能代替保存到提交阶段的训练元数据。

### 7.2 生命周期与逻辑游标

预测分配 → 慢预测确认/覆盖；独立进行 demand 发射 → cache 返回 → IFU 消费 → 后端提交/训练 → 释放。不能把这些完成时刻当成同一个指针。

需要分配、demand 发射、prefetch、提交/回收等逻辑位置；实际指针数量和实现待定。cache 接受请求只推进发射位置，不代表该 FTQ entry 可立即释放。

### 7.3 谁发请求

FTQ 侧主动提供 demand `valid` 和请求，ICache/发射控制返回 `ready`。仅 `valid && ready` 才发射、推进，并保证此前已获得返回队列容量。等待时请求与身份保持稳定。

概念请求包含：虚拟取指地址、FTQ 身份、返回槽身份以及必要上下文。普通请求直接取该 entry 对应的对齐 16B，入口/出口 mask 随元数据保留。具体信号位宽待定。

## 8. ICache 四拍流水线

正常命中、无资源冲突时每拍接受一个 demand 请求；四拍延迟不要求四个独立 bank，也不意味着一个 64B line 必须同时容纳四个请求。

| 阶段 | 逻辑工作 | 输出寄存内容 |
| --- | --- | --- |
| S0 | 并行启动 ITLB 与 cache tag/data 阵列访问 | 地址、身份、查询上下文 |
| S1 | 接收阵列数据；ITLB 命中比较、PPN/权限选择 | PAddr、翻译状态、cache tag/data |
| S2 | cache way tag 比较；PMP 范围匹配；PMA 属性判定 | way 命中候选、各 PMP 匹配候选、属性 |
| S3 | PMP 优先级与权限汇总；cache 数据选择；形成响应或 miss 请求 | 数据/异常/未命中及身份 |

这里是时序分工目标，尚无综合结果证明某目标频率可收敛。PMP 不能把所有范围计算、优先级、权限以及 cache 数据 mux 串在 S2。PMP 预解码/配置派生状态可在 CSR 修改时更新，具体电路待实现。

TLB miss 不是错误物理地址的 cache hit；翻译/权限/PMP 未完成时不能把数据交给指令流。异常响应也必须完成对应队列项，避免永远 pending。

目标为 VIPT 访问思路，注意 4KiB 页下索引与 bank 位必须落在页内偏移，或另行处理同义地址。曾举 16KiB/4-way/64 sets 的例子，**容量和路数并未定案**。

ITLB 第一版不额外增加多级结构或专用预取查询端口。ITLB 容量、相联度、reg/SRAM 实现仍需决策，不能根据四拍图推断为已经选定 SRAM TLB。

## 9. bank、回填与等待

### 9.1 整条 line 交错

64B line，两个 bank，`bank = address[6]`。页内 bit6 对虚实地址一致。

```text
0x000～0x03f → bank 0：含四个 16B 区域
0x040～0x07f → bank 1：含四个 16B 区域
0x080～0x0bf → bank 0
0x0c0～0x0ff → bank 1
```

**不是相邻 16B 交替分 bank**。一个 64B line 的四个 16B 区域都在同一 bank。16B 内暂不再分 bank。

每 bank 计划一个读口、一个写口。返回 16B 与回填数据宽度是不同参数，回填 beat 宽度尚未选择。tag/status 阵列也要核对端口，不能只给 data 分 bank 就宣布没有冲突。

### 9.2 冲突等待，不重做

回填写入期间，不允许尚未完整/合法安装的 line 参与有效命中。冲突请求保留等待，解除后继续；不能设计成不停取消并重新发射。

优先在 S0 接受前用 `ready=0` 阻止已知危险访问。已进流水线的请求若仍遇到必须等待的条件，应保留所在阶段状态并正确传递回压；已有安全读快照可以继续。不能宣称所有冲突都能在 S0 提前知道。

完整 line 可用后才发布有效状态，读写同地址同拍的 SRAM 行为要显式规避或定义。单独的读写端口不自动保证 read-during-write 数据正确。

必须保证 refill 能继续推进，不被等待该 refill 的 demand 反向堵死。精确到整 bank、set、way 或 line 的阻塞粒度待定；初版可以保守，靠事件统计评估代价。

### 9.3 hit under miss

需要类似 MSHR 的未完成 miss 状态、同 line 请求合并和 refill 跟踪。旧请求 miss 时允许后面的独立 hit 完成，但指令流按程序顺序消费。

等待策略不意味着遇到任何 miss 都全局停止。MSHR 数量、合并 fanout、被杀请求所占资源的释放、需求与预取保留份额待定。

## 10. 返回队列与 IFU

原始返回队列暂定 8 项，深度参数化。普通项保存 16B 原始数据、FTQ/请求身份、入口相关元数据、异常、pending/ready/killed 状态；确切布局待定。

请求发射前按程序顺序预留槽位，响应按身份写回，允许后发先回，队头满足条件才出队。若 demand 未真正握手，预留与取消规则必须避免泄漏或重复分配。

初版 killed 且仍 pending 的槽位保留至响应结束再回收；已返回的 killed 项可回收。该保守策略可能降低有效队列深度，需要测量。槽位不得提前复用后被旧响应覆盖；代际身份也要定义回绕安全条件。

理想命中时间示意：

```text
C0 S0 → C1 S1 → C2 S2 → C3 S3/写返回队列
C4 F0 → C5 F1 → 指令 buffer → 后端接收
```

队列不是固定额外“处理几拍”，驻留时间由慢预测、顺序依赖、跨块拼接和下游回压决定。上述图采用寄存队列后下一拍读取，不保证 bypass，也不把该图当成已定 RAM 实现。

F0 负责长度识别、拼接、RVC 展开，保留原 PC 与原始长度；F1 核对控制流类型、直接目标和预测，必要时发起修正。后续指令 buffer 可合并多个 FTQ 块的有效指令，每拍最多交付 4 条。

**待定**：F0/F1 每拍最多处理几个槽位、超过四条 RVC 时的保存方式、指令 buffer 深度，以及跨块补半字请求。这些决定峰值字节吞吐能否转化为稳定四条指令。

## 11. FTQ 驱动的预取

### 11.1 基本路径

FTQ 的独立 prefetch 游标走在 demand 前面，将预测路径上的地址按 64B line 去重，检查已在 L1/在途的 line，必要时向 L2 发请求，返回填入 ICache。预取数据不进入原始 demand 返回队列。

L1→L2→总线，当前范围单核，不引入完整多核一致性协议。FENCE.I 已选 D25 的整个本地 ICache 失效方案，见第 11.4 节。

预取只看 slow_done 的 FTQ entry 是候选策略，尚未冻结；领先距离、触发与节流条件待定。

### 11.2 地址翻译

- 初版保留单套 ITLB 与共享 PTW，不新增多级 TLB。
- 用小的近期页翻译记录复用有效映射；同虚拟页、匹配地址空间/权限上下文及页大小时，可拼接页内偏移得到物理地址。
- “同页不查 TLB”不意味着跳过权限、PMP/PMA，也不意味着只比较 VPN 即可。
- 跨页提前查询 ITLB；已有翻译时不应无条件 PTW，miss 才触发或合并页表遍历。
- 预取查询利用可用端口/仲裁，需求优先；没有额外端口就不能保证需求每拍满载时还同时查询另一虚拟页。
- SFENCE.VMA、上下文变化等必须使翻译复用记录正确失效；预取翻译失败不直接制造架构异常，未来 demand 再走异常路径。

### 11.3 与正常访问并行的条件

已完成翻译的预取，可以在另一空闲 bank 查询 tag，而需求使用自己的 bank。相同 bank 的两个读请求仍竞争读口；1R1W 解决不了两个读。

预取 refill 走写口，但同地址/安装状态冲突仍按等待规则处理。L2 队列、总线、MSHR、PMP 检查资源也是带宽约束，分 bank 不保证所有环节无限并行。

曾讨论让 L2 跟踪 L1I 驻留、绕过 L1 查询，**未选为第一版基线**。初版以 L1 本地过滤及在途合并为方向，具体过滤结构待定。

### 11.4 D25：FENCE.I 全量失效（已定）

**2026-09-30 决定，2026-10-02 补充数据侧实现**：用户选择“全清”本地 ICache，通常清 valid 位即可，不需要将 data RAM 写零。第一版不采用修改地址记录、定点失效、逐 store 通知 ICache 或每次 ICache miss 探测 DCache 的 I/D 一致性路径。对写回式 L1D，FENCE.I 另外扫描全部 DCache 元数据，把发现的每条脏行可靠写回 L2 并逐出；干净行不因此逐出。脏行处理复用 B08 的按物理行 clean+invalidate 能力，另加全行遍历与完成汇合，不要求每次都把 DCache 数据阵列或所有干净行清空。若所有有效行都脏，最差情况确实要处理全部这些行；选择这个低频但可能较慢的首版方案，不预设 FENCE.I 的实测频率。

第一版采用保守的同步顺序：

1. FENCE.I 到达可安全处理的提交边界，暂停新取指和预取，取消其后的已取指令及推测工作。
2. 等已提交 SQ store 全部得到 DCache 写完成确认并释放；随后遍历 L1D 的所有行，对脏行逐条执行写回 L2 并失效，等待每条写回确认及整个遍历完成。不能把请求被接受、SQ 项刚释放或向 L2 发出写请求当成已完成。借用 B08 的按行维护流程，但 FENCE.I 自身需要遍历控制；维护请求仍须为旧回填、写回与 DMA 行协调保留前进路径。
3. 等旧取指/预取及相关在途操作结束，确保不会在失效之后再次安装旧指令数据。
4. 使整个 ICache 失效，清除 F0 残留半字、返回/指令 buffer 中的旧路径内容，通过 D24 同步恢复推测上下文。
5. 在 SQ drain、L1D 脏行写回/逐出、旧取指隔离和 ICache 失效均确认完成后，允许 FENCE.I 标记完成并退休，从其后一条指令重新预测、取指。

全量失效会带来重新预热的代价，L1D 脏行逐出也会增加后续数据 miss。后端 B23 记录 `fencei_retired` 和 `fencei_dcache_evict_cycles` 两个 64 位逻辑计数器；以后结合后续 ICache/DCache miss 评估是否优化。扫描容量、写回端口、完成握手的具体 RTL 尚未实现或验证。

规范依据：RISC-V ISA v20260120，Zifencei 2.0，允许简单实现清空本地指令缓存与取指流水线，并要求后续取指观察到先前应可见的数据写入。参考 https://docs.riscv.org/reference/isa/v20260120/unpriv/zifencei.html 。D25 当前范围为单核本地同步。

### 11.5 D26：SFENCE.VMA 按地址与 ASID 失效（已定）

**2026-09-30 决定**：用户确认按规范两个寄存器操作数选择失效范围，以减少不必要的翻译清理；不采用此前建议的无条件全范围失效。当前仅记录设计，未实现 RTL。

`SFENCE.VMA rs1, rs2`：rs1 的值是虚拟地址，rs2 的有效低位是实现支持的 ASID。必须保留操作数寄存器编号是否为 x0 的信息，不能用读取值是否为零代替。

| 操作数 | 翻译失效范围 |
| --- | --- |
| rs1=x0，rs2=x0 | 所有地址空间的全部翻译，包括 global 映射 |
| rs1=x0，rs2≠x0 | 指定 ASID 的全部非 global 翻译 |
| rs1≠x0，rs2=x0 | 所有地址空间中覆盖指定虚拟地址的叶映射，包括 global 映射 |
| rs1≠x0，rs2≠x0 | 指定 ASID 中覆盖指定虚拟地址的非 global 叶映射 |

- ITLB、DTLB、预取翻译复用记录接收同一范围描述，匹配项清 valid，范围外项保留；若以后增加页表遍历缓存等翻译缓存，也必须纳入相应同步与失效范围。
- 地址匹配按每项实际页大小判断是否覆盖该地址，不能固定按 4KiB VPN 比较；所有匹配项都应处理，不能只清第一个命中项。global 属性要反映页表遍历路径上的有效 G 属性。
- 普通寄存器值为零仍是具体参数：例如 rs2=a1 且 a1=0 表示 ASID 0，而 rs2=x0 才表示所有 ASID。ASID 超出实现位宽的高位按规范忽略。
- 当 rs1 指定无效虚拟地址时不因该地址触发异常；按规范的无效地址情形处理。正常指令权限检查仍由特权指令处理流程负责。
- SFENCE.VMA 同时完成先前页表写入与后续页表访问之间所需的同步，不能只清 valid。必须等待或取消相关旧 PTW，防止失效后重新安装应被清除的旧翻译；前端后续取指不能继续使用被失效的旧映射或权限快照。具体等待/取消握手待实现。
- **2026-10-02 后端 B24 补充完成顺序**：SFENCE.VMA 作为串行指令到达 ROB 队头后，先等已提交 SQ 全量排空并确认先前 store 已写入共享 DCache；随后按上述地址/ASID 范围清理翻译缓存及隔离旧 PTW 回填，清除携带旧翻译的年轻取指，收到翻译同步完成确认后才允许退休和重新取指。首版不做 L1D 全量脏行写回；若 PTW 不再共享 DCache，须重新审查页表写入可见性。
- 第一版为本 hart 本地处理，不把本地 SFENCE.VMA 当作其他 hart 的同步。该决策不要求清空物理标记的 ICache 数据，也不替代 FENCE.I 的指令内容同步。

规范依据：RISC-V ISA v20260120，Supervisor-Level ISA 1.13，§11.1.2.1 与地址翻译过程中的推测 PTW 约束：https://docs.riscv.org/reference/isa/v20260120/priv/supervisor.html 。规范允许扩大失效范围，但本设计选择实现上述四种范围；ASID 位宽及翻译结构容量仍待定。

### 11.6 D27：satp 上下文切换与旧请求隔离（已定）

**2026-09-30 决定**：用户接受在安全处理 satp 写入时取消旧取指及旧 PTW、隔离迟到返回的方案。此前“等所有旧 PTW 完整结束，再写 satp 并重启”的保守建议不采用。

1. 合法 satp 写入在安全的架构处理边界生效，清除该指令之后的旧上下文指令和推测工作，按 D24 统一重定向并恢复历史/RAS。
2. 取消旧上下文的逻辑取指及 PTW 状态，更新翻译上下文；从该指令之后的 PC 重新预测、取指，使用新的有效上下文进行翻译与权限检查。
3. 已发出的旧内存事务允许自然返回，保留事务身份及取消标记直到返回完成；其结果不能作为新上下文的取指响应或翻译结果，也不能重新安装被取消的旧翻译。不得提前复用身份后被旧响应覆盖。
4. 不把“所有旧事务已经返回”作为新上下文重启的统一前提；但仍受可用请求槽和端口限制。若唯一 PTW 槽仍被旧事务占用，新 miss 可以等待，而 TLB 命中路径不应仅因旧遍历未结束而统一停住。
5. satp 写入本身不自动全清 TLB；保留的翻译按 ASID/global、翻译模式及所需上下文正确匹配。预取翻译复用记录也必须检查上下文，不能只比较 VPN。页表修改、ASID 重用所需的 SFENCE.VMA 仍按 D26 处理，D27 不替代该同步语义。

本决策不固定取消标记的编码、epoch 位宽、事务槽深度和恢复拍数，也不声称切换零周期。尚未实现 RTL 或测量性能。

参考核对边界：BOOM commit `58ef2720eae13be26b3008c02b5a74ce29c61c44` 的 v4 CSR 指令采用 unique/flush-on-commit 路径，分配等待 ROB 清空等条件；未固定其外部 Rocket TLB/PTW 依赖，不能推断所有 PTW 的完成策略。香山 commit `e7bab53e66dfb3c4a1d11cf9519b0396f8576cae` 中 satp 写入触发 flushPipe；翻译侧 flush 可取消 PTW 状态，L2TLB 的 waiting_resp/flush_latch 隔离迟到回填。该版本 wrapper 中 satp.changed 连接 ASIDChanged，不能把任何 satp 字段写入都描述成触发同样的 PTW flush。D27 是本设计选定的统一处理方式，不宣称逐项复制参考实现。

### 11.7 D28：PMP 修改后的前端同步（已定）

**2026-09-30 决定**：用户确认有效修改 PMP 配置后，统一清除年轻路径并重新取指，不额外清空 ICache。

- 合法且有效的 pmpcfg/pmpaddr 修改在安全架构处理边界生效；清除其后的年轻指令及旧权限检查结果，按 D24 恢复推测历史/RAS。
- 更新 PMP 范围预解码等派生状态，确保后续检查使用一致的新配置；然后从修改指令之后重新取指。
- ICache 数据可保留，cache 命中仍必须通过当前 PMP 权限检查。旧请求迟到返回按取消标记隔离，不能继续交付已经过时的权限结果。
- 对实现分页的 hart，软件修改 PMP 后按规范执行 SFENCE.VMA x0,x0，同步虚拟内存系统及可能缓存的 PMP 检查结果；复用 D26。硬件的流水线清除不替代软件所需的 SFENCE.VMA 语义。

参考：RISC-V Machine-Level ISA 1.13，Physical Memory Protection and Paging，https://docs.riscv.org/reference/isa/priv/machine.html 。尚未实现 RTL；与后端 CSR 提交、取消及完成接口的具体连接留待后端明确。

## 12. 性能事件与观测接口

目标：既能仿真输出，也能 FPGA 读出统计，判断表大小、队列深度、预取收益和稳定四条交付能力。以下是已接受的观测需求，信号名称为建议，不是已固定端口 ABI。

### 12.1 接口原则

- 各模块提供事件 valid/count 和必要分类；同拍多个事件不能被一个 Boolean 丢掉。
- 预留可参数化统计收集模块。FPGA 的 CSR/MMIO 地址、计数位宽、溢出规则、清零与一致快照机制待定。
- 仿真可增加按 FTQ 身份的 trace；硬件常驻计数与详细 trace 分开，避免为日志增加关键路径。
- 区分提交路径准确率、所有推测访问流量、取消流量。明确分子分母。
- 区分“发生几次”与“阻塞几拍”；共享阻塞原因可多热记录，但互斥归因另行定义，不能直接相加当总停顿。

### 12.2 事件清单

| 类别 | 至少预留的事件/状态 | 决策用途 |
| --- | --- | --- |
| uBTB | lookup/hit/miss；方向/目标错误；快慢结果一致/不一致 | 容量与快预测质量 |
| 快慢比较 | 快对慢对、快对慢错、快错慢对、快错慢错，按最终结果归类 | 判断覆盖净收益，不能把不一致都当快预测错 |
| TAGE | 有效条件预测次数、方向错误、provider 表、分配/替换等 | 历史与容量调整 |
| 目标 | target_missing、目标误预测、修正来源、损失周期 | 分清方向正确但取不到目标 |
| BTB 单目标 | 区域内 CFI 槽位切换、同 CFI 目标变化、区域替换 | 判断是否需要每 entry 多目标 |
| RAS | push/pop/pop-push、underflow/overflow、return 命中/错误、栈顶修复次数、恢复周期与被替换次数 | 深度与恢复成本；D29 取消 log 满事件 |
| 训练 | 训练次数/端口等待、执行到提交延迟 | 日后比较提前训练 |
| FTQ | 占用直方图、高水位、空/满周期、预测领先量、慢覆盖杀掉项数 | FTQ 深度与预测领先 |
| ICache | demand hit/miss、每 bank 读写、同 line 合并、refill 安装等待 | 组织与 MSHR 调整 |
| 冲突 | demand/refill、demand/prefetch 读冲突，事件次数与等待周期 | bank/端口是否值得增加 |
| 翻译 | ITLB hit/miss、同页复用、PTW demand/prefetch 请求与合并、翻译等待 | 是否需要额外 TLB 资源 |
| 预取 | 候选/发出/重复过滤/被节流、useful/late/unused eviction、错误路径流量 | 判断预取收益与污染 |
| MSHR | 占用、满、需求等待、预取占用、需求升级/合并 | 数量和保留份额 |
| 原始返回队列 | 0…8 占用直方图、高水位、pending/ready/killed 数、队头等待原因、满阻塞 | 8 项是否合适 |
| IFU | 跨 16B/line/page 拼接、长度修正、预解码重定向、下游回压 | 后处理吞吐 |
| 交付 | 可用指令数分布、实际交付 0/1/2/3/4 条、后端 ready/接受数 | 是否稳定提供四条 |

建议分别统计“后端愿意接收四条时，前端不足四条的周期”和“后端自身回压的周期”。不能用总交付量低直接归因前端。

预取 useful/late/unused 的严格定义以及 line 上 provenance 元数据待定；先保留可归因能力，避免后期只有总 miss 数无法判断效果。

## 14. 后续实现必须保持的不变量

- 每个返回能唯一关联到原请求；旧路径结果不能覆盖复用后的新槽位。
- 非 killed 的原始块只有在 slow_done 后才能进入 IFU。
- 指令始终按正确路径顺序交付，cache 响应可以乱序到达。
- 32 位指令跨块只拼接顺序地址的后半字，保留原 PC/长度。
- 有效目标必须属于当前选中 CFI；一个 BTB target 不能冒充其他槽位的目标。
- 请求等待时身份和负载稳定；接受一次只产生一次资源分配与 RAS/history 动作。
- PMP/翻译异常和 killed 请求都有完成/释放通路，不永久占住队头。
- 等待 refill 的 demand 不能阻止其所依赖的 refill 前进。
- 推测恢复完整覆盖历史 E/C；RAS 按 D29 修复索引、占用数和保存的栈顶，有意允许深层污染导致额外误预测；提交训练使用原预测上下文。
