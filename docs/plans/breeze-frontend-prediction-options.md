# Breeze RV64GC 前端分支预测：五维设计备选

记录日期：2026-10-10。目标平台：KCU105，四核顺序执行处理器。文档用途：保存设计选项、参考机制、选择理由与调优指标，随前端设计讨论逐项展开。

已确定：**GShare，方案②：全局历史推测更新并配套恢复；正常命中主通路流水化，持续每拍供给一条完整指令**。当前讨论重点：**预测与取指的流水关系**。全局历史的恢复结构、PHT 训练时机继续保留候选。各项容量和流水拍数通过后续工作负载分析、资源报告与时序报告确定。

## 1. 五个设计维度

| 维度 | 核心问题 | 需要记录的选择 |
| --- | --- | --- |
| ① 分支预测算法 | 方向和目标怎样产生？ | Bimodal、GShare、局部历史、Tournament、TAGE、感知机，以及 BTB、RAS、间接目标预测 |
| ② 历史更新时机 | 后续预测读到哪个执行进度的历史？ | 预测接收、执行解析、提交；全局历史、局部历史与路径历史各自的规则 |
| ③ 预测状态恢复 | 重定向后，历史与返回栈怎样接到保留的指令前缀？ | 历史快照、历史环形缓冲、版本队列、提交态副本、RAS 恢复记录 |
| ④ 预测表训练时机 | 实际结果何时进入预测表？ | 执行阶段训练、提交阶段训练、训练队列、写入合并与读写旁路 |
| ⑤ 预测与取指流水组织 | 预测结果何时可用，每拍能接受多少工作？ | 同步查表、流水查表、队列解耦、快速预测与后级覆盖、取指块内分支选择 |

五个维度可以组合。例如，GShare 可以搭配执行阶段历史更新，也可以搭配预测接收时的推测历史更新；预测表训练又可以选择执行阶段或提交阶段。组合时需要一起定义历史版本、训练元数据、队列所有权和重定向边界。

### 1.1 术语与分工

- **条件分支方向预测**：预测顺序执行或跳转执行。本文用 `0` 表示顺序执行，用 `1` 表示跳转执行。
- **BTB**：保存控制流指令的位置、类型和目标等信息，帮助前端提前产生下一取指地址。
- **RAS**：跟踪调用与返回，向返回指令提供目标地址。
- **间接目标预测器**：利用上下文预测 JALR 等指令的目标；ITTAGE 是一种候选结构。
- **GHR**：全局分支方向历史寄存器。
- **PHT**：保存方向计数器的模式表。BHT 在开源实现中常作为方向预测结构的整体名称；阅读 RTL 时同时核对字段和索引公式。
- **预测接收事件**：预测结果进入其所属队列的 `valid && ready` 事件。它为推测状态更新提供明确的时钟边界。

对 RV64GC，方向预测关注条件分支；调用、返回、直接跳转和间接跳转分别提供目标预测与控制流类型识别的设计需求。

### 2.2 Bimodal：PC 索引的两位饱和计数器

对于一张 `2^k` 项的表，可以采用下面的教学配置：

```text
pc_index = (PC >> 1) & (2^k - 1)
counter  = PHT[pc_index]
direction = counter[1]
```

RV64GC 支持 RVC，指令起始地址具有两字节粒度。因此，按指令地址索引时从 `PC[1]` 开始取位，也就是 `PC >> 1`。按取指块索引的实现还会使用块地址和块内位置；这两类索引规则分别记录在算法与流水组织中。

一种常见的两位状态编码为：

| 状态 | 方向倾向 | 预测方向 |
| --- | --- | --- |
| `00` | 强顺序 | 顺序执行 |
| `01` | 弱顺序 | 顺序执行 |
| `10` | 弱跳转 | 跳转执行 |
| `11` | 强跳转 | 跳转执行 |

实际方向为 `1` 时执行 `min(counter + 1, 3)`；实际方向为 `0` 时执行 `max(counter - 1, 0)`。计数器在两个端点饱和。

同一分支如果连续跳转，计数器逐步进入强跳转状态。循环退出一次后，它进入弱跳转状态；下一次循环进入时仍可预测跳转。这样的迟滞有利于学习稳定的方向倾向。

**调优重点**：表容量、初始状态、PC 哈希、表项共享竞争，以及预测读取与训练写入的端口安排。

### 2.3 GShare：PC 与全局历史共同选择计数器

当索引宽度与 GHR 宽度都是 `k` 时，教学配置为：

```text
pc_index = (PC >> 1) & (2^k - 1)
index = pc_index XOR GHR
direction = PHT[index][1]
```

例如，`pc_index = 101101`，`GHR = 001011`，则 `index = 100110`。这个表项学习的是“这个 PC 与当前历史上下文组合”的方向倾向。

GHR 比索引宽时，可把历史分段折叠到索引宽度；GHR 比索引窄时，可采用明确的扩展与混合规则。历史宽度和表项数是两个可以分别调整的参数。

**预测记录**：保存本次 `index`、方向和相应历史版本。实际方向到达后，使用保存的 `index` 访问训练表项。

**训练规则**：对该表项训练时的当前计数器做饱和加减。预测之后、训练之前，同一表项可能已经收到其他分支的训练；读写旁路或训练顺序规则负责串行化这些更新。

**历史规则**：GHR 可以在预测接收、执行解析或提交时移入方向。每种选择对应维度②与维度③中的一套机制。

**调优重点**：历史长度、表容量、哈希方式、历史新鲜度、共享竞争与恢复开销。本项目方向预测算法采用 GShare，参数在后续讨论中确定。

### 2.3.1 Taken-only BTB 与 NT 分支

`T` 表示跳转方向，`NT` 表示顺序方向。条件分支的类型识别和方向预测分别处理：BTB 命中提供提前的类型与目标，指令返回后的预译码确认真实类型，GShare 提供条件分支的方向倾向。

Taken-only 候选将实际跳转作为新 BTB 表项的分配资格。一个表项记住某条曾跳转的分支，后续方向仍由 PHT 提供。该分支实际取 NT 时，已有 BTB 表项按选定维护规则继续管理。

| 预测场景 | 前端动作 | 历史与训练 |
| --- | --- | --- |
| BTB hit，类型为条件分支，PHT 预测 NT | 顺序取指 | 预测接收时移入 0；执行时按实际方向训练保存索引对应的 PHT 项 |
| BTB miss，随后预译码确认条件分支 | 基础候选采用顺序方向作为本次预测 | 在分支识别与接收边界移入 0，保存恢复信息与训练索引；执行时按实际方向训练 |
| BTB miss，条件分支实际取 T | 执行阶段重定向到实际目标 | 恢复分支前历史并移入 1，训练 PHT，并分配 BTB 目标项 |

例如 `0x100` 的条件分支实际取 NT，继续执行 `0x100 + instLen`。预译码确定条件分支类型，方向历史记录 0，PHT 向顺序倾向训练，BTB 将新项容量留给实际取 T 的目标。此后该分支实际取 T 时，可以进入 BTB；后续即使 BTB 命中，PHT 仍可预测 NT。

晚级方向重预测是另一个流水组织候选：预译码识别分支并算出目标后，再按 PHT 方向决定后级覆盖。其历史更新、快照与覆盖边界在维度⑤逐项确定。

历史设计文本 `docs/frontend-prediction-design.md` 第 3、4 节记录 taken-only、S3 推测历史和检查点恢复。当前工作区源码的 GHR 接收执行解析方向，条件分支 BTB 更新覆盖 T 与 NT；本次重构的已确定选择记录在第 8 节。

### 2.4 局部历史：学习同一分支自己的方向序列

局部历史两级预测器首先用 PC 选择历史。例如，一个分支反复出现 `110110110` 的方向序列，局部历史记录这一位置近期的结果，模式表学习这些历史对应的下一方向。

模式计数器可以由多个历史项共享，也可以配在各个 PC 索引项内部。CVA6 的 `bht2lvl.sv` 采用 PC 对应项内的历史与计数器组，提供具体的 RTL 阅读样本。

**调优重点**：局部历史项数、每项历史位数、模式表共享方式、两级查询延迟，以及局部历史的版本管理。[S6]

### 2.5 Tournament：让选择器学习采用哪个预测器

一个典型组合是局部历史预测器加全局历史预测器。两者分别给出方向，选择器保存对两者的偏好。出现方向分歧时，根据实际结果训练选择器。

Alpha 21264 的设计论文给出局部、全局与选择器组成的实例。它适合作为“算法组合”和“历史、训练时机分别安排”的联合阅读材料。[S9]

**调优重点**：组件之间的互补程度、选择器学习速度、总存储容量，以及各组件访问和训练的并行度。

### 2.6 TAGE：多种历史长度，加标签识别上下文

TAGE 采用一个基础预测表和若干带标签的组件表。组件表使用按几何关系增长的历史长度，例如 `4、8、16、32` 位；这一组数值用于解释结构。

每张组件表分别计算：

```text
index_i = hash_index(PC, history[0:L_i], path_history)
tag_i   = hash_tag(PC, history[0:L_i], path_history)
```

路径历史按具体方案选配。长历史通过折叠映射到固定宽度索引和标签。

典型组件项包含标签、方向计数器和 usefulness 状态。基础表提供起始预测，标签匹配的组件提供候选预测；通常选择使用历史最长的匹配组件作为 provider，alternate 提供备选预测。置信度与 alternate 选择策略进一步决定最终方向。

训练涉及方向计数器、usefulness、组件分配和替换管理。预测元数据保存 provider、alternate、索引、标签和历史版本中训练规则需要的字段。[S11]

**调优重点**：组件数、各组件容量、历史长度、标签宽度、分配策略，以及多表查找到 provider 选择的流水延迟。

对四核 FPGA，TAGE 的评估同时覆盖表存储、标签比较、优先选择、历史折叠、训练带宽与恢复记录。容量相近的方案可以具有多种逻辑路径和端口需求。

### 2.7 感知机：对历史特征加权求和

原始感知机方案用 PC 选择一组有符号权重，把历史方向编码为 `+1/-1`，计算：

```text
y = w0 + Σ(w_i * x_i)
y >= 0：预测跳转执行
y <  0：预测顺序执行
```

这里 `w0` 表示方向偏置，`x_i` 表示历史特征。对于 `+1/-1` 特征，硬件通过权重加减实现乘积。

训练以实际方向和预测置信度为依据，调整偏置与各历史权重。基础形式为 `w0 += t`、`w_i += t*x_i`，并配合阈值与有符号饱和规则。

感知机用一组权重覆盖较长历史，适合加权相关性和线性可分模式。多种特征与混合组件进一步扩展模式覆盖。[S12]

**调优重点**：权重精度、历史长度、加法树深度、预测延迟、训练更新量、特征选择与训练阈值。

### 2.8 CBP：算法、论文与模型的资料入口

用户所说的 “champin” 对应 **Championship Branch Prediction，CBP 分支预测竞赛**。

CBP 汇集参赛预测器、论文、模型和评测框架。CBP 2016 的公开方案包括 TAGE-SC-L、Multiperspective Perceptron、感知机与 TAGE 组合等。[S14]

TAGE-SC-L 由 TAGE、Statistical Corrector 和 Loop Predictor 组成。TAGE 提供主预测，统计校正器结合历史、方向偏置和置信度进行校正，循环预测器学习稳定迭代次数的退出位置。[S13]

竞赛模型提供算法容量和预测质量的参考；FPGA 选型再加入查表端口、读写冲突、预测流水、恢复记录、LUT/FF/BRAM 用量和布局布线频率。评价数据同时记录工作负载、预测延迟与取指供给条件。

## 3. 维度②：历史更新时机

本维度讨论 GHR 移入方向位的时间。PHT 两位计数器的训练时机在维度④讨论。

例如，按程序顺序先出现条件分支 A，再出现条件分支 B。预测 B 时，A 可能还在前端队列或执行流水中。预测接收更新让 B 使用包含 A 预测方向的历史；执行解析更新让 B 使用已解析分支的实际方向历史；提交更新让 B 使用已提交分支的实际方向历史。

| 方案 | 后续预测使用的历史 | 主要收益 | 工程代价与观察重点 |
| --- | --- | --- | --- |
| 执行解析时更新 | 已解析分支的实际方向 | 状态流直接接到执行结果，易于建立初始模型 | 记录预测时的历史滞后量；后端停顿会改变历史新鲜度 |
| 提交时更新 | 已提交分支的实际方向 | 与架构保留的执行序列对齐 | 记录执行至提交的距离；结合前端队列深度评估历史新鲜度 |
| 预测接收时推测更新 | 较老在途分支的预测方向 | 将前端当前路径纳入历史，覆盖连续分支相关性 | 保存恢复位置；方向、目标和预译码校正共同维护历史版本 |
| 分层历史 | 提交态副本加推测态工作历史，必要时配阶段影子 | 同时支持前端预测与架构边界恢复 | 明确各副本的更新事件、旁路路径和重定向优先级 |

### 3.1 推测更新的时钟约定

1. 在历史更新前保存该预测的历史位置或快照。
2. 在预测结果进入所属队列的接收事件上移入预测方向。
3. 队列停顿时保留状态；再次推进时由接收事件触发下一次更新。
4. 条件分支、直接跳转、间接跳转和调用返回参与历史的规则分别定义。

教学用 GShare 可先采用“条件分支每条贡献一个方向位”的规则。按取指块组织的实现还可选择块级历史编码，记录分支位置和方向之间的关系。

### 3.2 用在途分支数选择方案

平均分支密度用于估计典型占用，队列容量和执行停顿边界用于确定恢复资源上界。连续条件分支、等待操作数的分支、前端继续填充队列等场景决定峰值在途分支数。

**记录指标**：预测至解析周期数、解析至提交周期数、历史滞后分布、在途分支平均值与峰值、前端预测队列占用。

### 3.3 论文阅读：历史推测更新的量化分析

《Speculative Updates of Local and Global Branch History: A Quantitative Analysis》的主线是量化历史推测更新的收益，并给出配套恢复结构。[S15]

- 研究对象：全局、局部与混合历史预测器。
- 比较策略：提交更新；推测更新加恢复；推测更新后直接延续历史，重定向时保留已有 GHR。
- 实验平台：八发射乱序模型，11 个 SPEC95 程序。
- 核心发现：历史新鲜度与在途分支数量影响预测和 IPC；推测更新与恢复共同提供收益。
- 全局恢复结构：历史快照、扩展历史、推测版本队列。
- 本项目阅读顺序：先用该论文理解维度②的更新选择，再用第 3.3 节理解维度③的恢复组织。

### 3.4 三种策略的结果与实现取舍

| 策略 | 主要收益 | 实现取舍与实验观察 |
| --- | --- | --- |
| ① 提交更新 | GHR 保存已提交的实际方向，控制直接 | 历史跟随提交进度；在途数量变化会改变预测时的历史位置 |
| ② 推测更新加恢复 | 提前纳入较老分支方向，重定向后接回保留路径 | 保存恢复信息并组织状态回写；论文整数程序表现支持该组合 |
| ③ 推测更新后延续历史 | 预测阶段及时推进 GHR，恢复存储需求较小 | 被替换路径的方向继续参与索引；论文多数程序中①的性能高于③ |

论文第 3.2 节报告：八发射乱序模型、16 位 GHR、64K 项 PHT、最多 32 条在途分支条件下，②相对①的 SPECint 平均加速约 10%，`go` 达到约 31%。增加在途容量的独立实验采用理想化 PHT，多数整数程序的收益趋势在 4–8 条容量附近趋于平缓。[S15]

2026-10-10，用户确定本项目采用②：全局历史推测更新并配套恢复。具体恢复结构进入下一轮讨论，决定记录在第 8 节。

## 4. 维度③：预测状态恢复

恢复的目标是让推测状态对应重定向后保留的执行前缀，再从新的 PC 继续预测。全局历史、局部历史、路径历史和 RAS 分别记录恢复规则。

### 4.0 论文术语与恢复对象

论文第 3.3 节讨论预测使用的**全局历史状态**。History-Based 类把推测历史放在工作 GHR 中，快照和扩展历史是其具体组织；Future-Based 类把推测版本放在队列中，GHR 保存提交态历史。恢复动作分别作用于工作 GHR 或推测版本队列。[S15]

论文中的 **PHT** 保存方向计数器，其更新按训练规则安排。第 4.3 节讨论局部历史恢复，其中 **BHT** 保存各个 PC 索引位置的历史位串。阅读该论文时，分别使用“全局历史 GHR”“局部历史表 BHT”和“方向计数器表 PHT”三个名称。

本项目已确定的 GShare 以全局历史状态作为本轮恢复对象；PHT 训练时机在维度④讨论。

| 方案 | 恢复材料与动作 | 适用条件 | 资源与控制要求 |
| --- | --- | --- | --- |
| 每预测单元保存 GHR 快照 | 从快照恢复，再追加保留的实际结果 | 短 GHR、小型顺序核 | `K × H` 位原始历史快照，加有效位和关联标识 |
| 扩展历史或环形历史缓冲 | 保留历史位，检查点保存位置；重定向恢复位置和折叠状态 | 长历史或较多在途预测 | 历史保留长度、环绕规则、折叠历史恢复规则 |
| 在途历史版本队列 | 按预测顺序保存版本，用保留前缀定位工作历史 | 队列化预测路径 | 版本分配、顺序释放、提交态衔接 |
| 提交态副本 | 提交维护基准历史，架构边界重定向时接回基准 | 异常、中断等提交边界事件 | 提交推进与重定向同拍时的选择规则 |

快照、扩展历史和版本队列的组织方式可参考 Skadron 等人的历史更新研究。[S15]

### 4.1 重定向事件与恢复边界

| 事件 | 保留的执行前缀 | 状态动作 |
| --- | --- | --- |
| 条件分支方向校正 | 分支之前的指令，加该分支实际方向 | 恢复分支前历史，再移入实际方向 |
| 条件分支目标校正 | 分支之前的指令，加该分支实际方向 | 同时恢复较年轻预测贡献和取指队列 |
| 直接或间接跳转目标校正 | 跳转之前的指令，加该跳转规定的历史贡献 | 恢复检查点，再应用该指令保留的状态动作 |
| 前端预译码校正 | 预译码确认的指令边界与控制流前缀 | 修正控制流类型、块内历史和较年轻预测 |
| 异常、中断、权限或序列化重定向 | 由架构事件确定的保留前缀 | 接回对应的历史与 RAS 基准，并切换取指 epoch |

### 4.2 RAS 恢复

RAS 需要维护栈指针、栈内容和调用返回操作。推测 push 可能覆盖环形栈中较早的内容；追求精确恢复时，可选择保存被覆盖内容的撤销记录、版本化栈，或保存足够的栈快照。

指针与栈顶快照也是一种容量较小的方案，其调优指标包含恢复后返回目标命中率和较深栈内容的保存范围。选择时把“保存哪些状态”和“返回预测质量”写成明确的设计参数。

RV64GC 调用的返回地址使用 `PC + instLen`；`instLen` 由实际指令长度确定，包含两字节与四字节形式。

### 4.3 顺序核的解析历史副本与提交历史副本

执行解析确定分支的实际方向与目标；提交确定架构保留的指令序列。这两个事件分别定义历史副本的含义。

对于“较老分支解析并处理重定向后，较年轻指令才产生有效执行结果”的顺序流水，可比较以下恢复候选：

- `specGHR`：预测接收时移入预测方向，供 GShare 索引使用。
- `resolvedGHR`：按程序顺序，在有效分支解析时移入实际方向。
- 分支重定向：计算 `resolvedNext = append(resolvedGHR, actualDirection)`，再令 `specGHR = resolvedNext`。
- 分支方向与目标预测一致：更新 `resolvedGHR`，`specGHR` 继续保存较年轻分支的推测贡献。

这套候选利用顺序解析的实际历史形成恢复基准。异常、中断和其他架构重定向按各自的保留边界安排恢复信息；提交态历史副本可用于提交边界恢复。

`committedGHR` 加 `specGHR` 描述两种进度的历史副本。论文的 Future-Based 进一步为各条在途分支保存推测历史版本，预测读取最新版本，恢复截断并修正队列，提交将队首版本转入提交态 GHR。[S15]

本轮继续比较分支前检查点与顺序解析实际历史两种恢复候选，具体选择随流水的解析、提交与重定向规则确定。

## 5. 维度④：预测表训练时机

历史推进产生下一次预测的上下文；预测表训练学习实际执行结果。两者各自拥有更新事件和状态存储。

| 训练方案 | 结果进入表项的时机 | 主要收益 | 工程代价与观察重点 |
| --- | --- | --- | --- |
| 执行解析训练 | 分支产生实际方向与目标时 | 实际结果较早影响后续预测，元数据释放较早 | 规定较老异常与重放下的训练资格；评估被替换路径的训练贡献 |
| 提交训练 | 分支进入保留的提交序列时 | 训练序列与架构执行序列对齐 | 保存元数据至提交；评估训练滞后和短循环复用 |
| 预测阶段推测训练 | 预测接收时按预测方向调整计数器 | 较早改变表项的方向强度 | 对预测值进行强化；精确撤销需要表状态和训练顺序记录 |

训练队列是写端口调度方式，可搭配执行或提交产生的训练事件。队列保存索引与实际方向，待端口可用时按训练顺序写表；设计记录其容量、排队延迟、同项连续训练和读写旁路规则。

### 5.1 各算法的训练记录

| 算法 | 建议保留的信息 |
| --- | --- |
| Bimodal | 表项索引、预测方向、关联指令或预测块标识 |
| GShare | 预测索引、预测方向、历史快照或历史位置 |
| 局部历史 | PC 历史项、预测使用的局部模式位置、历史版本 |
| Tournament | 各组件预测结果和索引、选择器索引、最终预测源 |
| TAGE | provider、alternate、所需索引与标签、置信度、历史版本及分配相关信息 |
| 感知机 | 权重项索引、历史特征或其引用、求和值或训练阈值所需信息 |

实际方向和目标随解析或提交信息补齐。计数器与权重更新按照训练时的表状态和并发更新规则执行。

### 5.2 执行解析与提交训练的时间例子

假设 A 在预测时读取的表项为 `01`，实际方向为跳转。教学流水中，A 在时刻 T0 被预测，在 T3 解析，在 T5 提交。

| 时刻 | 执行解析训练 | 提交训练 |
| --- | --- | --- |
| T0 预测 A | 读取 `01`，保存索引 | 读取 `01`，保存索引 |
| T3 得到实际方向 1 | 按实际方向训练到 `10` | 保存实际方向，表项保持原训练进度 |
| T5 提交 A | A 的训练记录已经处理 | 按实际方向训练到 `10` |

时刻与阶段对应关系用于说明机制。训练结果被预测读取的具体拍数由表端口、写入流水和旁路规则确定。

Rocket 的 BHT 接口按分支解析结果更新；CVA6 的 `frontend.sv` 将解析分支的有效位、PC 和实际方向送入 BHT。BOOM 文档通过 FTQ 保存预测信息，提交时训练。[S4][S16][S7]

### 5.3 GShare 的训练索引与计数器状态

预测时先确定索引，并随分支保存：

```text
预测时：pc_index = 101，GHR = 011
训练记录中的 index = 101 XOR 011 = 110
```

执行时，工作 GHR 可能已经变为 `110`。训练仍使用记录的 `110` 表项索引，维持本次预测与实际结果的关联。

本项目的串行训练候选使用更新时的当前计数器值：

```text
actualDirection = 1：PHT[index] ← min(PHT[index] + 1, 3)
actualDirection = 0：PHT[index] ← max(PHT[index] - 1, 0)
```

例如，两条分支都训练同一项，原值为 `01`，实际方向都是 1。顺序处理后为 `01 → 10 → 11`。表读写冲突、更新旁路和训练队列共同维持这个更新顺序。

### 5.4 训练资格与推测训练的状态要求

执行训练以有效条件分支解析事件为起点，明确同拍较老重定向、异常、停顿和重放的优先级。提交训练以保留序列中的条件分支提交事件为起点。基础 GShare 候选对每条符合资格的条件分支按实际方向训练一次，包含方向预测一致的情况。

推测训练按预测方向强化计数器；实际方向到达后，需要规定其校正与最终训练规则。计数器饱和以及多个分支共享同项决定了精确撤销所需的信息。例如 `11` 经跳转强化后仍为 `11`，保存原值可用于精确恢复；同项交错训练还需保留各次更新的顺序关系。

当前讨论建议以实际方向训练作为主方案，继续比较执行解析与提交两个时机。该建议与全局历史的推测更新规则分别记录。

## 6. 维度⑤：预测与取指流水组织

**预测延迟**描述请求到结果所需的拍数，**预测吞吐**描述每拍可接收的请求数。例如，两拍延迟、每拍一笔请求的预测器可以在流水填满后每拍产生一个结果。

下一 PC 对预测结果存在依赖。前端每拍产生连续的正确路径请求，还需要安排早期预测、提前计算或队列供给等机制。

| 组织方式 | 数据流 | 主要收益 | 工程代价与观察重点 |
| --- | --- | --- | --- |
| 预测与取指紧耦合 | 当前 PC 查预测与指令缓存，结果推进下一 PC | 控制和状态关联直接 | 预测路径、缓存返回和下一 PC 选择共同决定供给间隔 |
| 流水查表 | 索引、读表、选择分布在多个阶段 | 便于安排同步存储和短组合路径 | 处理下一 PC 依赖、历史旁路与训练读写冲突 |
| 预测队列解耦 | 预测产生取指块描述，缓存侧按队列消费 | 吸收预测和缓存服务节奏变化 | 队列容量、预测领先距离、epoch、恢复与历史保留范围 |
| 快速预测加后级覆盖 | 快速组件先产生下一 PC，后级组件提供覆盖结果 | 同时利用短延迟和丰富上下文 | 后级覆盖代价、预测版本关联和年轻请求处理 |

### 6.1 RV64GC 取指块的设计项目

- 取指块字节数、缓存读端口宽度、每拍交付指令数分别定义。
- 压缩指令与四字节指令通过真实起始位置关联预测项。
- 跨取指块、跨缓存行与跨页的指令拼接保存 PC、长度和异常归属。
- 一个块包含多条条件分支时，确定最早控制流选择、块内历史推进和预测输出数量。
- 返回数据按请求标识与 epoch 关联到取指块；队列恢复和数据接收拥有明确优先级。

BTB 容量、方向表容量和 RAS 深度与流水级数共同调优。同步存储的延迟、端口配置和旁路逻辑通过 FPGA 综合与实现报告评估。

### 8.3 旧方案与当前取指通路对照

2026-10-10 阅读源码，版本为 `9747dfebf61930c1f4a9934b2a8aab6425ae72ff`。旧方案来源为 [`frontend-prediction-design.md`](../frontend-prediction-design.md)，其中保留 S1 查预测表、S2 取指响应、S3 预解码校正及六项 fetch buffer 的级划分，并提出以下组合：

| 机制 | 旧方案提出的行为 | 当前源码行为 |
| --- | --- | --- |
| BTB | 条件分支实际 taken 时分配新项，已有项继续更新；返回采用 RET 类型 | 每次有效 BTB 更新选择已有项或分配新项；JALR 由 BTB 提供目标 |
| GHR | S3 条件分支被 fetch buffer 接收时移入预测方向，每条指令携带更新前历史检查点 | 后端 EX 产生实际方向更新，前端移入 GHR |
| PHT | 保留预测时索引，后端按实际方向训练 | EX 使用随指令携带的索引产生训练信息 |
| RAS | 八项，S3 推测 push/pop，S1 通过 BTB 的 RET 类型读取栈顶；检查点保存指针与栈顶 | 返回目标沿用 JALR 的 BTB 预测路径 |
| 预取 | 下一行预取与两行缓冲，需求读和预取各一笔在途 | Cluster 中预取请求 valid 固定为零 |
| 参数 | BTB 32 项、GHR 10 bit、PHT 1024 项 | 具体实例由配置决定 |

Git 记录中，2026-08-21 的 `e5e1f1e` 引入 RV64C、Sv39 与 Linux 平台支持，指令拼接器和取指翻译适配器在该版本采用单请求状态机。2026-10-05 的 `d5672f5` 加入上述预测器改进文档，文档选择沿用当时取指级划分。

当前压缩指令路径使用一个在途指令上下文，拼接器依次推进 `Idle → RequestFirst → InspectFirst → Emit → Idle`。在取指字缓冲命中、指令完整位于该字、下游持续接收的条件下，按寄存器状态转换计算，请求接收间隔为四拍。新取指字经过请求与返回状态，跨字指令经过第二字处理状态。

翻译适配器依次推进 `Idle → Translate → CacheReq → CacheWait → Idle`，下一请求在当前响应交付后接收。TLB 与 ICache 阵列的并行查询覆盖同一请求内部的工作。在压缩指令路径中，下一 PC 随当前指令返回的长度产生。

流水组织讨论以正常命中路径的吞吐为依据：单发射后端每拍接收一条指令，前端各级同时保存各自上下文，持续供给每拍一条完整指令。RVC 拼接、下一 PC 生成、翻译与缓存查询共同定义请求接收间隔；缺页遍历、缓存补行等多拍事件由局部控制状态推进。后续逐项确定这些阶段的接收、交付、停顿与重定向规则。

### 8.6 CVA6 FPGA 取指与预测的逐拍对齐

以第 8.4 节固定版本的 FPGA 配置、`FpgaAlteraEn = 0`、普通 BHT 为例，TLB 与 ICache 持续命中，队列持续接收。将请求、缓存命中返回、返回寄存后的处理分别标为 F0、F1、F2，计数范围从取指地址发出至完整指令进入取指队列。

| 阶段 | 取指工作 | 预测工作 |
| --- | --- | --- |
| F0 | PC 发出请求，启动缓存阵列读取 | 顺序地址推进 |
| F1 | 检查命中并返回取指块，拍末寄存数据和对应 PC | 返回端 PC 启动同步 BTB 读取，结果跨时钟边界到达 F2 |
| F2 | 取寄存后的块做 RVC 拼接、预解码，完整指令和预测信息进入队列 | 寄存后的 PC 组合读取 BHT，RAS 提供栈顶；结合 BTB 结果、指令类型和立即数形成目标 |

在该配置中，BTB 同步读跨越 F1/F2 边界，BHT 异步读在 F2 内完成。条件分支的 BHT 方向与 PC 加立即数组合在 F2 形成；普通 JALR 在 F2 结合预解码类型使用 BTB 返回目标。预测目标在 F2 组合送往请求端，新的目标请求可以在同拍进入 F0。[S19][S20][S25]

对齐依靠同一取指块的 PC：F1 用返回端 PC 读取 BTB，同时把块数据与 PC 寄存；F2 中 BTB 输出与数据寄存器对应同一块，BHT 使用该块寄存后的 PC。块内指令按各自起始地址的半字位置选择预测槽；跨块指令使用首半字所在块保留的 `btb_q` 与 `bht_q`。[S19]

### 8.7 前端与后端的流水级计数

讨论候选前端 S0/S1/S2/S3 与后端 ID/EX/MEM/WB 串接时，每段独立占一拍的组织对应八个主逻辑阶段。阶段之间的寄存器边界决定最终物理拍数，取指队列另行记录空队列通过延迟与排队等待。

后端设计第 3 节将 ID/EX/MEM/WB 定义为四级执行与提交路径，WB 后的 W2 完成已提交普通寄存器结果写入。计数到 WB 提交时使用四级后端口径；计数到 W2 物理写入时包含附加写入阶段。

流水深度描述单条指令经过的时钟阶段，稳态吞吐描述相邻指令的接收与交付间隔。八段流水在每级持续接收与交付的条件下，可以同时容纳不同指令，并持续每拍交付一条。前端阶段划分继续结合预测反馈、RVC 拼接、翻译与缓存读取边界逐项确定。

### 8.8 八级顺序流水的公开先例

### 8.9 Cortex-A53 与 Cortex-A320 的性能参照

Cortex-A53 与 Cortex-A320 作为本项目的商业顺序核参照。A53 采用八级双发射顺序流水，A320 采用八级单发射顺序流水。A320 的发射宽度更接近本项目；A53 的公开跑分提供可量化的比较起点。[S27][S28]

| 核心与平台 | 公开性能指标 | 测试口径 |
| --- | --- | --- |
| Cortex-A53，NXP LS1043A | 4.18 CoreMark/MHz；3.06 DMIPS/MHz | NXP 64 位核心性能数据，CoreMark 使用 `-O3` 与编译选项调优 [S29] |
| Cortex-A53，TI AM62x | 单核 3557 DMIPS，约 3 DMIPS/MHz | 1.2 GHz，GCC 9.2、`-march=ARMv8 -O3`，Linux 5.10 [S30] |
| Cortex-A320 | SPECINT2K6 标量性能相对 Cortex-A35 提升超过 30% | Arm 发布的相对性能结果，参照核心为 A35 [S28] |

CoreMark/MHz 表示每单位频率的任务吞吐效率。以 4.18 CoreMark/MHz 为算术参照，100 MHz 对应约 418 CoreMark；该换算用于设定频率归一化的比较尺度，最终成绩由各平台实测确定。

第一轮比较采用单核标量 CoreMark/MHz，记录源码、编译器、编译选项、缓存配置与运行环境。后续加入相同输入任务的周期数，并用各核心自身的 IPC、前端停顿、分支校正次数和缓存访问统计解释表现。跨指令集的任务比较以完成相同工作的周期和时间为尺度。

四核阶段分别记录独立任务的总吞吐、共享数据任务的加速比与实际运行频率。A320 的 NEON/SVE2 和 int8 GEMM 数据归入向量与矩阵处理比较；当前 RV64GC 标量比较采用整数与标量浮点任务。[S28]
